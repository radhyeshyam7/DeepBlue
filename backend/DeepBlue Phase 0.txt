🔷 ARCHITECTURE EXPLANATION (BLOCK BY BLOCK)
1️⃣ UPI Mobile App

User enters amount and payee

Clicks “Pay”

No PIN yet

This is where transaction intent is created.

2️⃣ Transaction Intent Layer

Captures intent as an event

Ensures zero money movement

Triggers fraud analysis pipeline

👉 This layer is the entry point of your system.

3️⃣ User Profile & History Store

Stores:

Average transaction amount

Frequent recipients

Account age (for cooling-off)

Past cancellations / warnings

👉 Enables personalized detection, not generic rules.

4️⃣ Feature Extraction Engine

Converts raw data into risk features:

Examples:

Is this a new payee?

Is the amount unusually high?

Is this happening at an odd time?

Did the user hesitate before paying?

Is the user new to UPI?

This runs in milliseconds.

5️⃣ Risk Detection Engine

This is the brain.

It has three sub-parts:

a) Rule-Based Engine

Transparent

Explainable

Immediate red flags

b) ML Anomaly Detector

Detects deviation from user’s normal behavior

Catches subtle patterns

c) Intent Analyzer

Uses user’s selected payment reason

Boosts risk for scam-related intents

6️⃣ Payee Trust Scoring Module

Evaluates receiver risk, not just sender behavior.

Payee classified as:

Trusted

New / Neutral

Unverified / Risky

Displayed visually to the user.

7️⃣ Risk Scoring & Decision Unit

All signals are combined into a single risk score (0–100).

Risk bands:

Low → Allow

Medium → Warn

High → Delay / Block

This avoids binary “fraud / not fraud” thinking.

8️⃣ Alert & Mitigation Layer

This is where fraud is actually prevented.

Includes:

Plain-language explanations

Smart delay countdown

Cooling-off rules for new users

Extra confirmation if needed

Still before PIN.




1️⃣ USER PROFILE & HISTORY STORE

👉 This is your memory.
👉 Without this, there is no personalization.

Think of it as a per-user behavioral snapshot.

🔹 A. BASIC USER METADATA (Static / Slowly Changing)

You store this once and update occasionally.

| Field                               | Why it matters          |
| ----------------------------------- | ----------------------- |
| `user_id`                           | Unique identifier       |
| `account_age_days`                  | New users are high-risk |
| `total_transactions`                | Experience level        |
| `first_transaction_date`            | Maturity check          |
| `last_transaction_date`             | Activity pattern        |
| `user_type` (new / regular / heavy) | Adaptive thresholds     |


🔹 B. TRANSACTION BEHAVIOR STATISTICS (Very Important)

| Field                         | Explanation             |
| ----------------------------- | ----------------------- |
| `avg_transaction_amount`      | Baseline behavior       |
| `median_transaction_amount`   | Robust against outliers |
| `max_transaction_amount`      | Upper comfort limit     |
| `std_dev_amount`              | Volatility in spending  |
| `transactions_per_day_avg`    | Normal frequency        |
| `transactions_per_week_avg`   | Pattern stability       |
| `preferred_transaction_hours` | Time-of-day habits      |

1️⃣ LIST OF API ENDPOINTS

POST /transaction/intent

POST /transaction/decision

POST /transaction/feedback

No other endpoints are required for MVP.

2️⃣ API ENDPOINT DETAILS
🔹 Endpoint 1: Submit Transaction Intent

Purpose
Capture transaction intent and behavioral signals before PIN entry.

Method
POST

Path
/transaction/intent

Request JSON
{
  "user_id": "string",
  "amount": 5000,
  "payee_id": "string",
  "intent_type": "refund | receive | purchase | support",
  "behavioral_signals": {
    "hesitation_time_ms": 1800,
    "amount_edit_count": 2,
    "confirmation_delay_ms": 3200
  }
}

Response JSON
{
  "transaction_id": "string",
  "status": "RECEIVED"
}

🔹 Endpoint 2: Get Risk Decision

Purpose
Determine risk level and required user intervention.

Method
POST

Path
/transaction/decision

Request JSON
{
  "transaction_id": "string"
}

Response JSON
{
  "risk_level": "LOW | MEDIUM | HIGH",
  "action": "ALLOW | WARN | DELAY",
  "reason_codes": [
    "new_payee",
    "amount_spike",
    "intent_mismatch",
    "unusual_time",
    "hesitation_detected"
  ]
}

🔹 Endpoint 3: User Feedback

Purpose
Capture user action after warning or delay for adaptive learning.

Method
POST

Path
/transaction/feedback

Request JSON
{
  "transaction_id": "string",
  "user_action": "PROCEEDED | CANCELLED"
}

Response JSON
{
  "status": "ACKNOWLEDGED"
}

3️⃣ FEATURE VECTOR FIELDS LIST

(Used internally for ML inference)

Each transaction is converted into the following behavioral feature vector:

Feature Name	Description
amount_ratio	amount / user_avg_amount
amount_zscore	deviation from user mean
is_new_payee	whether payee is unseen
payee_trust_score	relationship strength (0–1)
payee_payment_count	past payments to payee
txn_frequency_recent	recent txns vs baseline
velocity_spike	sudden frequency increase
time_deviation_score	deviation from usual hours
is_unusual_hour	outside preferred window
confirmation_time_ratio	confirm time vs baseline
hesitation_score	pause & edit-based signal
amount_edit_count_ratio	edits vs normal
intent_risk_score	inherent intent risk
intent_direction_mismatch	intent vs txn direction
user_maturity_flag	new / regular / heavy
cooling_off_active	protection state
recent_warning_ignored	ignored previous warning
device_change_flag	new device detected

ML outputs:

{
  "anomaly_score": 0.0 – 1.0
}

4️⃣ RISK LEVEL DEFINITIONS (LOCKED)
🟢 LOW RISK

Transaction matches normal user behavior

No unusual context detected

Action: Allow silently

🟡 MEDIUM RISK

Mild behavioral deviation detected

Some risk signals present

Action: Show warning, allow continuation

🔴 HIGH RISK

Strong behavioral deviation

Multiple high-risk signals

Action: Delay transaction and require intent confirmation
